# citylights_crackme_1
[citylights_crackme_1](https://crackmes.one/crackme/5ab77f5f33c5d40ad448c7dd)
Тренировочная программа второго уровня сложности.
Исполняемый файл идет вместе с его библиотекой в отдельном файле, CrackThisApp.exe и CrackThisApp.dll соответственно.
При запуске просит ввести 9 значный пароль, при этом надо вводить каждую цифру в каждую ячейку отдельно, при нажатии на кнопку идет проверка результата.
## Итог
Решений множество: keygen скрипт позволяет сгенерировать каждый верный ключ по порядку.
Алгоритм генерации ключа был воссоздан из логики проверки входных данных - значений матрицы 3x3: ее определитель должен обладать несколькими свойствами, которые накладывают ограничения на входные параметры.
Разбор и оформление отчета заняли около 8 часов в сумме, где большую часть заняла математика.

## 1. Первичный осмотр
Быстрый осмотр в DIE показал, что это 32-битное приложение:

![](img/Pasted%20image%2020261024224253.png)

Анализ секций в PE-bear не показал аномалий: имена секций стандартные и размер выделяемой памяти и размер на диске особо не отличаются, никакая секция не содержит разрешений RWX или WX.
Но поскольку это 32-битное приложение, нужно определять верно соглашение о вызовах у каждой функции отдельно. Компилятор Borland C++ использует соглашение `__fastcall` в основном, но это не правило, поскольку экспортируемые функции почти всегда имеют либо `__cdecl`, либо `__stdcall`. Их различие можно визуально определить: чистит стек вызывающий (`__cdecl`) или вызываемая сторона (`__stdcall`).

## 4. Сборка своего генератора ключей
Вернулся к трем выражениям и думаю, как их упростить. Первое что заметил, это по сути сборка числа: берем цифру и ставим ее на свой разряд. Но поскольку все три выражения сравнивают с одним и тем же числом => они равны между собой. 
Приравниваю первое со вторым:
$$e_1 = e_2$$
Путём сокращения общих слагаемых прихожу к равенству:
$$p_1 \bmod 10 = p_6 \bmod 10$$
Значит, последняя цифра первого и шестого аргументов равны.

Приравниваю первое с третьим:
$$e_1 = e_3$$
Путем сокращения общих слагаемых:
$$p_1 \bmod 10 = (p_2 \bmod 10) + 3$$
Из этого следует, что последняя цифра первого аргумента равна последней цифре второго аргумента + 3, но это накладывает следующие границы для двух аргументов:
$$p_1 \bmod 10 \in [3, 9], \quad p_2 \bmod 10 \in [0, 6]$$
Оценим диапазон правой части:

$$10000 \cdot (p_5 \bmod 10) \in [0, 90000]$$

$$1000 \cdot (p_1 \bmod 10) \in [3000, 9000]$$

$$100 \cdot ((p_3 /\!/ 10) \bmod 10 + 5) \in [500, 1400]$$

$$10 \cdot ((p_9 /\!/ 10) \bmod 10) \in [0, 90]$$

$$(p_7 \bmod 10) + 2 \in [2, 11]$$
Суммируя границы для первого выражения, получаем:

$$\det \in [3502,\ 100501]$$
Для двух других выражений диапазоны такие же, как и должно быть при равенстве.


Верхнюю границу значений каждого элемента матрицы определителя можно грубо оценить, перемножив его числа: ~100000 это три числа 40-50 помноженные между собой. Это дает нам верхнюю границу для перебора параметров.
Для получения верного набора параметров я решил сначала рассчитать каждое возможное значение первого выражения e1. Затем используя вычисленные выражения, я попытался перебрать возможные комбинации для определителя матрицы. Делать я это решил, выражая определитель матрицы через третью строку:
$$p_7 \cdot (p_2 \cdot p_6 - p_3 \cdot p_5) + p_8 \cdot (p_3 \cdot p_4 - p_1 \cdot p_6) + p_9 \cdot (p_1 \cdot p_5 - p_2 \cdot p_4) = \det$$

Далее выразим девятый аргумент, чтобы нам не пришлось перебирать этот параметр:
$$p_9 = (e_1 - p_7 \cdot (p_2 \cdot p_6 - p_3 \cdot p_5) - p_8 \cdot (p_3 \cdot p_4 - p_1 \cdot p_6)) / (p_1 \cdot p_5 - p_2 \cdot p_4)$$
Подумав немного, я решил, что заранее вычислять выражение `e1` нам не нужно, сделаю это уже перебирая наши 8 аргументов, при этом отбрасывая те, которые не подходят по условиям. Поскольку нам нужен девятый аргумент как второй разряд выражения, в подцикле перебираем десяток девятого параметра. Через необходимые условия проверяем значение полученного определителя матрицы:

```python
# det = e1
# p7*(p2 p6 - p3 p5) + p8(p3 p4 - p1 p6) + p9(p1 p5 - p2 p4) = e1
# p9 = (e1 - p7*(p2 p6 - p3 p5) - p8(p3 p4 - p1 p6)) / (p1 p5 - p2 p4)     при этом p1 p5 =/= p2 p4 и p9 - целое
R = range(15)
key_count = 0
for p1, p2, p3, p4, p5, p6, p7, p8 in product(R, repeat=8):
    if p1 % 10 != p6 % 10:
        continue
    if p1 % 10 != (p2 % 10 + 3):
        continue
    C = p1*p5 - p2*p4
    if C == 0:
        continue
    # считаем e1 внутри цикла, чтобы не вычислять все дважды
    for d9 in range(10):
        e1 = 10000 * (p5 % 10) + 1000 * (p1 % 10) + 100 * ((p3 // 10) % 10 + 5) + 10 * d9 + (p7 % 10 + 2)
        num = e1 - p7*(p2*p6-p3*p5) - p8*(p3*p4-p1*p6)
        # если есть остаток от деления - отбрасываем, p9 - целое
        if num % C:
            continue
        p9 = num // C
        if p9 < 0:
            continue
        # проверяем десяток, чтобы совпадал
        if (p9 // 10) % 10 != d9:
            continue
        if calc(p1,p2,p3,p4,p5,p6,p7,p8,p9):
            key_count += 1
            print([p1,p2,p3,p4,p5,p6,p7,p8,p9]);
            break
    if key_count:
        break
```
Спустя около минуты ожидания, цикл находит верные ключи, их вывод я ограничил до одного ключа. Подставляя любой из выведенных ключей в программу, она выводит окно о верном результате.

## Что нового узнал

### 1. Динамическая загрузка функций
В списке функций я не нашел функций для проверки результата, но и в таблице импорта тоже нет подозрительных имен. Еще до анализа в Ghidra я думал, что логика проверок скрыта в `.dll`. Внутри `.exe` я обнаружил следующую конструкцию:
```asm
00402145  PUSH  s_CrackThisApp.dll_004691fa        ; "CrackThisApp.dll"
0040214a  CALL  KERNEL32.DLL::LoadLibraryA         ; eax = хендл
0040214f  MOV   dword ptr [EBP + local_d0],EAX     ; сохраняем хендл
00402155  CMP   dword ptr [EBP + local_d0],0x0     ; проверяем, пустой ли хендл, то dll не загрузилась
0040215c  JNZ   LAB_004021ba
0040215e  MOV   word ptr [EBP + local_b4],0x38
00402167  MOV   EDX,s_DLL_Not_Found!_0046920b      ; "DLL Not Found!"
```
Функция передает название `.dll`, чтобы загрузить данную библиотеку динамически, `LoadLibraryA` передаст в `eax` хендл, по которому другие функции могут взаимодействовать с `.dll`. Это делается при вызове `calc` при проверке ввода:
```asm
004025d7  PUSH  s__calc_00469247                   ; "_calc" имя функции
004025dc  PUSH  dword ptr [EBP + local_d0]         ; хендл DLL
004025e2  CALL  KERNEL32.DLL::GetProcAddress       ; eax = адрес calc
004025e7  MOV   dword ptr [EBP + local_11c],EAX    ; сохраняем адрес calc
004025ed  PUSH  dword ptr [EBP + local_118]
                ...
0040261d  PUSH  dword ptr [EBP + local_d8]
00402623  CALL  dword ptr [EBP + local_11c]        ; вызов calc по адресу
00402629  ADD   ESP,0x24
0040262c  TEST  EAX,EAX
0040262e  JZ    LAB_00402757
00402634  PUSH  s_You_got_it!_0046924d             ; "You got it!"
```
Здесь `GetProcAddress` достает адрес функции, находя ее по ранее полученному хендлу и названию функции, которое сохранено в коде программы. 
Изучив информацию, я узнал, что это частый прием малварей, чтобы маскировать функции: строка с именем функции шифруется, а таблица импортов чистая. Конкретно здесь имя `_calc` лежит открытой строкой.

### 2. Применение линейной алгебры
Кто бы мог подумать, что знания из первого курса пригодятся: в этой задаче нужно было вспомнить, как считается определитель матрицы и как его вычислить, используя разложение по строке.

### 3. Изменение типа возврата
Гидра автоматически определила тип возврата `calc` как `undefined8` (8 байт, `edx:eax`), вероятно из-за того, что внутреняя функция `FUN_00401478` возвращает ответ в таком виде. Но по логике в `.exe` проверяется по сути `True/False` из `eax`. Поэтому я самостоятельно переопределил тип возврата на int (4 байт), и гидра пересобрала декомпилированный код.
