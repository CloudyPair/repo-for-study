## 2. Поиск способа распаковки
В статическом анализе посмотреть на код упакованной секции не получится, поэтому я собираюсь найти момент, когда упаковщик передаст исполнение новой секции. Для этого я открываю наш `.exe` в CodeBrowser. 
Около entry я сразу вижу адрес возврата после распаковки:
```asm
14000c464  LEA   RSI,[DAT_14000a000]              ; RSI = источник (сжатые данные, RVA 0xA000)
14000c46b  LEA   RDI,[RSI + -0x9000]              ; RDI = 0x140001000 — приёмник (UPX0)
14000c472  PUSH  RDI                              ; сохраняем OEP на стек
```
Зная оригинальный entry point (OEP), можно в дебагере, например, x64dbg поставить брекпоинт и дальше анализировать содержание/сделать дамп для будущего анализа.
В дебагере x64dbg я попробовал поставить брекпоинт прямо по смещению `bphws hard.exe:0x1000, x`,  но при снятии первоначального брекпоинта исполнение проскакивает этот брекпоинт, не триггерив его. Я предполагаю, что это из-за настроек виртуальной машины. 
Теперь я попробую найти в стабе упаковщика момент, где завершается передача прав новой распакованной секции. Для этого ставлю `bp VirtualProtect` и разбираюсь, где последний раз эта функция будет вызвана. Как только брекпоинт срабатывает, я ступаю до `ret` с помощью Ctrl + F9, потому что брекпоинт сработает внутри `kernel32.dll`. Это позволит вывести на завершающий код стаба внутри самого `.exe`: 

| адрес            | инструкция                    | комментарий                                        |
| ---------------- | ----------------------------- | -------------------------------------------------- |
| 00007FF73DD5C6AA | mov rcx,rdi                   | rcx:ZwProtectVirtualMemory+14                      |
| 00007FF73DD5C6AD | call rbp                      | последний вызов VirtualProtect                     |
| 00007FF73DD5C6AF | add rsp,28                    |                                                    |
| 00007FF73DD5C6B3 | pop rbp                       | восстановление регистров (зеркально push в начале) |
| 00007FF73DD5C6B4 | pop rdi                       |                                                    |
| 00007FF73DD5C6B5 | pop rsi                       |                                                    |
| 00007FF73DD5C6B6 | pop rbx                       |                                                    |
| 00007FF73DD5C6B7 | lea rax,qword ptr ss:[rsp-80] |                                                    |
| 00007FF73DD5C6BC | push 0                        | цикл для обнуления 128 байт стека                  |
| 00007FF73DD5C6BE | cmp rsp,rax                   |                                                    |
| 00007FF73DD5C6C1 | jne hard.7FF73DD5C6BC         |                                                    |
| 00007FF73DD5C6C3 | sub rsp,FFFFFFFFFFFFFF80      | возврат rsp на исходное место (вверх на 0x80)      |
| 00007FF73DD5C6C7 | jmp hard.7FF73DD52B90         | tail jump в OEP                                    |

В конце кода стаба мы видим прыжок в более нижние адреса, чем текущая инструкция. Поставлю брекпоинт на этот адрес, и сразу после этого брекпоинта попадаю в код новой секции. 

Изучая структуру новой секции, я могу заметить, что это стартовый код до инициализации `main`: существует пролог и эпилог у функций, между функциями находится два `int3` (байт `CC`), использование `gs:[30]` для обращения к TEB (thread environment block). Про сам UPX можно сказать однозначно: стаб один, и после него UPX ничего не распаковывает. Но что именно идёт за tail jump - программа или стаб другого упаковщика однозначно сказать нельзя. Исходя из сложности крякми я бы предположил, что здесь код программы.

Не заходя дальше, я хочу сохранить дамп для дальнейшего статического анализа:
![](img/Pasted%20image%2020261025225544.png)
Для этого Ctrl + I -> Scylla -> IAT Autosearch. Нажатие этой кнопки автоматически попытается заполнить Import Address Table (IAT): Scylla автоматически подставит OEP распакованной секции из текущего `RIP`, но нужно проверить, совпадает ли он с найденным OEP. Также Scylla заполнит поле VA - виртуальный адрес, где Scylla нашла таблицу импортов, и поле Size - размер этой таблицы. 
Нужно подключить в дамп найденные импорты, для этого нажимаем Get Imports. Однако не все импорты могут опознаться. Можем попытать удачу и просто удалить Thunk, который не определился, но это всего лишь позволит запустить приложение, не факт, что оно будет работать нормально и не крашнется.

Далее нужно создать дамп. Для этого нажимаем Dump и сохраняем. Но этот дамп будет содержать только образ кода из памяти и перепишет в заголовке точку входа на ту, что мы указали. При этом таблица импорта будет ссылаться на адреса, привязанные к текущему запуску `.exe`. Чтобы поправить структуру IAT, существует кнопка Fix Dump: она восстанавливает таблицу импорта по именам функций. Благодаря этому при следующем запуске загрузчик Windows сам заполнит IAT актуальными адресами, как у обычного exe.

## 3. Анализ распакованной секции
Во-первых, дампнутый `.exe` запускается, но сразу закрывается, вероятно те несколько неопределенных импортов были нужны для успешной работы, но это только одно из предположений. Открываем файл в CodeBrowser и автоанализируем.
По строкам ничего найти не удается, поэтому я открываю окно с импортами и ищу за что можно ухватиться. Вижу, что есть MSVCP140.dll - рантайм стандартной библиотеки C++, отсюда можно увидеть `std::cin` или же `operator>>`. Выбираю operator>>, поскольку он всегда будет участвовать при вводе пользователем пароля. Дважды кликаю на этот оператор и вижу 4 референса:
![](img/Pasted%20image%2020261026142402.png)
Проверив каждый на окружение: загрузку строк, проверку `memcmp`; я нашел, что только первый референс имеет такое окружение. Но чтобы поставить на него брекпоинт, я должен узнать смещение. Для этого я копирую адрес инструкции, которая меня интересует, `7ff7cd781870` и вычитаю из него ImageBase `7FF7CD780000`, который я узнал из PPEE дампа. Получаю смещение RVA `0x1870`. 
Открываю оригинальный `.exe` с помощью того же x64dbg, ставлю брекпоинт на `hard.exe+0x1870`, но только после загрузки всего кода, т.е. на инструкции tail jump. Таким образом, когда я ввожу пароль, этот брекпоинт срабатывает:
![](img/Pasted%20image%2020261026143043.png)
Здесь я вижу типичную загрузку двух строк перед сравнением: загружается буфер объекта строки MSVC, проверка, является ли этот буфер указателем на кучу. Первая проверка проверит сначала длину строк, вторая через `memcmp` содержание строк. В окне Dump перехожу на адрес буфера первой строки и в целом тут виден пароль - строка, с которой сравнивают вход:
![](img/Pasted%20image%2020261026143633.png)
Повторный запуск показал, что, действительно, пароль это `e4444`.

## Что нового узнал
### 1. Упаковка кода
Изучил на практике, как определять признаки упаковки путем анализа VirtualSize и RawSize, энтропии и имен секций. В данном примере использовался только один слой упаковки, но никто не говорил, что на месте распакованной секции будет код программы: есть вероятность, что это будет код другого стаба и/или проверка на подключенный отладчик внутри. 
### 2. Tail jump
В упаковщиках существует такое понятие, как tail jump. Означает оно последнюю инструкцию/jump перед передачей исполнения новой развернутой секции кода. Его можно обнаружить по характерным признакам: восстановление регистров и прыжок в другую секцию.
### 3. Поиск логики от ввода
В этой программе нужных строк было не видно в статике, поэтому я пошел с другого фронта: если программа принимает ввод пользователя и использует `std::cin`, то можно проанализировать места, где находится оператор >>. Но поиск по оператору не сработал бы всегда: здесь, например, `operator<<` не нашелся в окне импортов. Проверив `std::cout`, я обнаружил этот оператор, но он был в виде обычной функции - FUN_7ff7cd782500. То же самое было с крякми первой сложности. Объясняется это так, что компилятор помещает шаблонные функции (template) из C++ прямо в секцию кода.
### 4. ScyllaHide
В процессе поиска решения, как сделать дамп, я наткнулся на плагин ScyllaHide. Он позволяет скрывать подключенный отладчик, обходя множество проверок исполняемого кода на наличие отладчика. Это полезный в практике плагин, но в учебных целях я его использовать пока не планирую.

### 5. Перевод адресов
Scylla записала в ImageBase дампа базу того запуска. Чтобы вычислить адрес инструкции в запущенном приложении, необходимо вычислить `RVA = адрес в дампе - ImageBase`. После этого можно поставить на этот RVA брекпоинт, но только в тот момент, когда стаб исполнил tail jump т.е. первая инструкция новой секции, иначе брекпоинт не сможет поставиться - на том месте будет мусор.
