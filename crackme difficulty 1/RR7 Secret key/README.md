## 1. Первичный осмотр

Я использую программу Detect It Easy для анализа `.exe`.

![](img/Pasted%20image%2020261023142806.png)

Из данного окна я вижу, что это Windows-бинарник (PE64): разрядность приложения - 64 бита, архитектура - AMD64, тип приложения - консольное. Значит, снова имеем дело с соглашением о вызовах Microsoft x64. Компилятор - MinGW, при этом отладочная информация сохранена, поэтому в Ghidra будут видны имена функций. Размер файла небольшой, так что программа залинкована динамически.
## 2. Поиск проверки
Открываю файл в дизассемблере, чтобы автоматически проанализировать его, после этого открываю программу в дебаггере через dbgeng с флагом 0x12, чтобы программа открылась в отдельном окне.
Из-за отладочной информации мне доступны понятные имена функций (`main`, `printf`, `scanf`). Проходя через окно Defined strings, нахожу первую строку вывода, нажимаю `References` -> `Show References To Address` и перемещаюсь на первую загрузку адреса - `lea`. Тут видно, что адрес строки загружается как первый аргумент `printf`. 
Далее видно, что кладется во второй аргумент `scanf` - `rdx` - адрес на стеке `rbp-0x4`, в этот адрес будет загружен ввод пользователя. В первый аргумент `rcx` пойдет адрес строки с содержанием `%i`, т.е. `scanf` запишет 4 байта integer ввода пользователя. 
Следующим я нахожу, что мы введенное число сравниваем с числом `0x21`, если неверный ввод прыгает в завершение программы, а затем аналогичная проверка ввода пользователя (с сохранением уже на `rbp-0x8`) с числом `0x66`. В результате успешных проверок программа выводит `Congratulations, you have completed the challenge!`.

```asm
1400014cc  LEA   RAX=>local_c,[RBP + -0x4]                              ; rax = адрес local_c (rbp-0x4)
1400014d0  LEA   _Argc,[DAT_140004015]                                  ; rcx = "%i"
1400014d7  MOV   _Argv,RAX                                              ; rdx = rbp-0x4
1400014da  CALL  scanf                                                  ; scanf("%i", &local_c)
1400014df  MOV   EAX,dword ptr [RBP + local_c]                          ; eax = введенное число
1400014e2  CMP   EAX,0x21                                               ; равно 33?
1400014e5  JNZ   LAB_140001520                                          ; нет: завершение программы
1400014e7  LEA   RAX,[s_Enter_The_Secret_Key_:_140004018]               ; rax = "Enter The Secret Key : "
1400014ee  MOV   _Argc=>s_Enter_The_Secret_Key_:_140004018,RAX          ; rcx = rax
1400014f1  CALL  printf
```
## Что нового узнал
### 1. Поведение при отключенной оптимизации
При неоптимизированном коде компилятор чаще кладет результаты в `rax`, чтобы затем переложить в другие регистры результат.
### 2. Порядок аргументов в `printf` и `scanf`
Дополнительно напомнил себе, в каком порядке идут аргументы в этих двух функциях и как это выглядит в ассемблере.
### 3. Свойство `%i`
Ввод пользователя мог быть как `33`, так и `0x21` в hex или `041` в oct.
А второе число `102` соответственно `0x66` или `0146`.
